Client Credentials Grant

Machine-to-machine (M2M) authorization (RFC 6749 §4.4). There is no human user and no browser redirect. The client application authenticates directly with the identity provider using its own credentials to obtain an access token.

⚙️ Automated Daemon Execution: Ideal for backend microservices, scheduled cron jobs, ETL pipelines, and API integrations. Because client secrets cannot be safely kept in client-side code, this flow runs strictly server-side via our backend proxy (/api/client-credentials).

How Client Credentials Grant Works

Unlike user-centric flows that require an authorization code dance, the client credentials grant is a streamlined, single-legged protocol:

  1. Autonomous Machine Authentication: The background service operates under its own identity rather than delegating on behalf of an end user. There are no login prompts, MFA gates, or browser redirects.
  2. Direct HTTP POST to Token Endpoint: The client sends a single POST to the IdP's token endpoint with grant_type=client_credentials, client_id, client_secret, and the desired scope.
  3. Credential & Permission Verification: The IdP verifies the client secret and inspects which application roles or API scopes have been granted to this client registration by a directory administrator.
  4. Access Token Issuance: The IdP returns an HTTP 200 containing an access_token (typically valid for 1 hour).
  5. Why There is No ID Token or Refresh Token: An id_token asserts the identity of a human who logged in; because no user is present, an ID token is not issued. Similarly, refresh tokens are not provided because the machine client can simply request a fresh access token whenever needed using its stored secret.
