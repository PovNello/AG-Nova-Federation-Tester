SCIM 2.0 Server

Automated push-based identity provisioning (RFC 7643 & RFC 7644). The identity provider (Entra ID, Okta, etc.) monitors employee lifecycle changes and pushes user/group events to your SCIM endpoint in real time. This page acts as that target service provider and exposes every incoming raw payload.

💡 Educational Architecture: In standard SCIM, software hides the HTTP calls behind SDKs. Here, this page runs a full SCIM 2.0 compliant server. You can see the discovery handshakes, pre-flight queries, creation payloads, and PATCH operations exactly as the identity provider transmits them.
⚠️ Localhost detected: Entra ID cannot reach your local machine directly. Deploy this project to Vercel or use a reverse proxy tunnel (such as ngrok or Cloudflare Tunnel) to receive real provisioning calls from Entra ID. You can still test locally using the curl example below.
⚠️ In-memory storage: Running with ephemeral in-memory storage fallback. On Vercel, requests may hit different serverless instances. Connect an Upstash Redis database (KV_REST_API_URL) in your Vercel project storage tab for shared persistent state.

How SCIM Push Provisioning Works

Unlike SAML or OIDC (which authenticate users at login time), SCIM handles identity lifecycle management in the background: accounts are provisioned before users ever attempt to log in, and deprovisioned immediately when they leave. Here is the standard protocol sequence:

  1. Discovery & Feature Handshake: When setting up provisioning, the IdP sends GET /ServiceProviderConfig, GET /Schemas, and GET /ResourceTypes to discover which capabilities the server supports (e.g., authentication schemes, maximum filter results, bulk limits, and PATCH support).
  2. Pre-flight Existence Check: Before creating an account, the IdP queries GET /Users?filter=userName eq "john@example.com". If the user does not exist (totalResults: 0), it moves to creation. If the user already exists, the IdP captures the server's id to synchronize attributes rather than producing a duplicate.
  3. User Provisioning: The IdP issues POST /Users with the standardized SCIM JSON payload (names, emails, active status, and optional enterprise extensions like department or manager). The server creates the identity and returns HTTP 201 Created with a server-generated unique id.
  4. Incremental Updates (Delta Sync): When an employee's title, department, or status changes, Entra avoids full-object replaces. Instead, it sends a PATCH /Users/{id} containing fine-grained Operations (e.g., replace: {"title": "Staff Engineer"}).
  5. Group & Membership Synchronization: Groups are managed via POST /Groups, and members are added or removed dynamically using PATCH /Groups/{id} by referencing each user's SCIM id.
  6. Deprovisioning (Lifecycle Termination): When an account is disabled or unassigned in Entra, the IdP typically performs a soft-delete first by sending PATCH /Users/{id} with active: false. If hard deletion is configured, it subsequently sends DELETE /Users/{id}.
🔒 Authentication & Security: Every request is authenticated using a Bearer token in the Authorization: Bearer <token> header. Passwords sent during creation are masked in the audit log and never written to persistent storage.

Connect Entra ID (or Test via curl)

Configure an Enterprise Application in Microsoft Entra to push identities to your new endpoint:

  1. Create Enterprise App: In Entra admin center → Enterprise applications → New application → Create your own application (select "Integrate any other application you don't find in the gallery (Non-gallery)").
  2. Configure Provisioning: Open the app → Provisioning → Get started. Set Provisioning Mode to Automatic.
  3. Authorize Endpoint: Expand Admin Credentials, paste the Tenant URL and Secret Token from Step 1, then click Test Connection. Notice in Step 3 below that Entra immediately executes a test query (GET /Users?filter=...) to verify reachability.
  4. Assign Users & Groups: Under Users and groups, assign test accounts you wish to provision.
  5. Run Provisioning: Use Provision on demand to immediately push a single user through Entra's evaluation pipeline, or click Start provisioning to initiate scheduled background cycles (runs every ~40 minutes).
