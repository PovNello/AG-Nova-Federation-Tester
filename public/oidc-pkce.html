Authorization Code + PKCE

Proof Key for Code Exchange (RFC 7636) — the modern, browser-safe OIDC flow for public clients (Single Page Applications and Mobile Apps). No client secret is used; cryptography executed in the browser guarantees that only the client that initiated the request can redeem the authorization code.

🌐 Pure Browser Execution: Single Page Applications run in untrusted user environments and cannot securely conceal a secret. PKCE completely deprecates the legacy, insecure Implicit Flow by pairing local cryptographic hashing (via the browser's Web Crypto API) with direct CORS calls to the IdP.

How Authorization Code + PKCE Works

PKCE prevents the Authorization Code Interception Attack where a malicious actor or extension snoops the redirect URL to steal the auth code. Here is the step-by-step cryptographic sequence:

  1. Cryptographic Key Generation (Local): Before contacting the IdP, the browser creates a high-entropy secret string (code_verifier) using crypto.getRandomValues(). It then hashes this verifier using SHA-256 and base64url-encodes the digest to produce the code_challenge. The verifier stays safely in the browser's local memory.
  2. Front-Channel Authorization (GET /authorize): The browser redirects the user to the IdP's login page, appending response_type=code, code_challenge, and code_challenge_method=S256. The IdP authenticates the user, records the challenge with the session, and prompts for consent.
  3. Authorization Code Redirect: Upon approval, the IdP redirects back to the registered redirect_uri with an authorization code in the query string. Even if an attacker intercepts this code in browser history, they cannot use it without the unhashed verifier.
  4. Back-Channel Token Exchange (POST /token): The browser makes a direct HTTP POST (via fetch) to the token endpoint, presenting the code and the original plain code_verifier. The IdP computes SHA256(code_verifier): if the hash matches the recorded challenge, it confirms the caller is authentic and issues tokens.
  5. Token Reception & Claims: The IdP returns an id_token (JWT asserting the user's identity) and an access_token (bearer token for API calls).
