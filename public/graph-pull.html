Graph API Pull

Automated pull-based identity synchronization. Your application authenticates directly to the Microsoft Graph REST API as itself (machine-to-machine) and imports targeted users from Microsoft Entra ID using OData inclusion filters. This page executes and reveals every step of the query and ingestion pipeline.

💡 Pull vs Push: While SCIM relies on Entra pushing events into an inbound webhook, Graph Pull makes outbound HTTPS calls only (graph.microsoft.com). This makes it ideal for nightly batch imports, on-demand synchronization, or services running behind private corporate firewalls. Required Application permission: User.Read.All (with admin consent).

How Pull-Based Sync Works

In a pull architecture, the client application controls when to synchronize, which identities to query, and how to ingest them into its local database. Here is the complete protocol lifecycle:

  1. Machine-to-Machine Authentication (OAuth 2.0 Client Credentials): Because sync jobs run as unattended background services without a human user, the application authenticates directly as itself (RFC 6749 §4.4) against the tenant's token endpoint (/oauth2/v2.0/token) using its registered Application (Client) ID and Client Secret.
  2. Application Scopes & Roles (/.default): The app requests scope https://graph.microsoft.com/.default. Microsoft Entra returns an Access Token containing tenant-wide Application Roles (such as User.Read.All) that have been pre-approved by a directory administrator via Admin Consent.
  3. Targeted Inclusion Filtering (OData): Enterprise directories often contain thousands of service principals, guest accounts, and shared mailboxes. The application constructs an OData query ($filter) to select only active, relevant employees (e.g., department eq 'Sales' and accountEnabled eq true).
  4. Graph Advanced Queries (ConsistencyLevel: eventual): Standard queries are strictly consistent. However, advanced filters (such as ne, endsWith, or searching custom directory extensions) leverage Entra's distributed indexing layer. Microsoft Graph requires passing the ConsistencyLevel: eventual header and $count=true.
  5. Batch Ingestion & Cursor Pagination (@odata.nextLink): Graph returns matching users in pages (default 100). If more users match, Graph provides an opaque cursor URL (@odata.nextLink). The application loops through these pages to import and reconcile all identities in its local store.
