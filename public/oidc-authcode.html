Authorization Code + Client Secret

The standard OIDC flow for confidential clients (traditional server-rendered web applications such as Node.js, Python, .NET, Java, or Next.js server components). The client uses a private client_secret stored securely on the backend server to prove its identity during token redemption.

🔒 Server-to-Server Security: The front-channel (browser) handles user interaction and obtains a temporary authorization code. The critical token exchange is executed server-to-server via our backend proxy (/api/token-exchange) so your client_secret never touches client-side browser code or network inspection tools.

How Authorization Code Flow Works (Confidential Clients)

Unlike public clients (SPAs), confidential web applications possess a private backend server. This architecture splits the flow cleanly into two distinct communication channels:

  1. Front-Channel User Redirection (GET /authorize): The user clicks "Sign In" in your application. The browser redirects to the IdP's login portal with response_type=code, client_id, and a cryptographic state token. The user enters credentials, performs MFA, and grants requested permissions.
  2. Authorization Code Handover: Upon successful authentication, the IdP redirects the user's browser back to the application's backend redirect_uri, passing an ephemeral authorization code in the query string. This code is single-use and expires in minutes.
  3. Back-Channel Direct Token Exchange (POST /token): Your backend web application intercepts the incoming code and initiates a direct, machine-to-machine HTTPS POST to the IdP's token endpoint, authenticating itself with its private client_secret.
  4. Token Security & Session Creation: Because tokens are delivered directly to your backend server over a TLS-encrypted back-channel, the browser never sees the access or refresh tokens. Your server creates an HTTP-only, secure session cookie for the user, rendering the flow immune to browser XSS token-theft attacks.
  5. Token Decoding & Claims: The application validates the cryptographic signature of the id_token and extracts user profile claims (sub, email, name) to initialize the local user session.
