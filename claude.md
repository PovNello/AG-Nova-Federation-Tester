## 🚀 Project Overview
An educational, provider-agnostic tester for **SAML 2.0** and **OIDC** federation flows. 
Unlike standard client libraries, it **does not hide** intermediate steps or raw payloads. It exposes exact HTTP requests/responses, deflated XML, and decoded JWTs for learning and debugging purposes.

## 🛠️ Key Features & Logic

### OIDC Implementation
- **Step 0 Protocol Narratives**: All 4 OIDC flow pages (`oidc-pkce.html`, `oidc-authcode.html`, `oidc-clientcreds.html`, `oidc-device.html`) feature dedicated Step 0 cards detailing the protocol lifecycle, security mechanics (public vs confidential clients, interception defenses, M2M autonomy, and cross-device decoupling), and field-by-field guidance.
- **PKCE Generation**: Native Web Crypto API used in `shared.js` to create `code_verifier` and `code_challenge` (S256).
- **Token Decryption**: Custom JWT decoder in `shared.js` splits tokens into Header/Payload/Signature without external libs.
- **Token Truncation**: Long tokens are truncated in UI for readability but remain copyable in full.
- **Parameter Extensibility**: Supports adding arbitrary URI parameters (e.g., `prompt`) via dynamic tables.
- **Device Flow Polling**: Real-time polling with "Slow Down" and "Pending" state handling. Supports both public and confidential clients (optional `client_secret`).

### SAML 2.0 Implementation
- **SAML Request**: Generated by the backend (`/api/saml-request`) using `zlib` for DEFLATE compression.
- **ACS Endpoint**: Reusable endpoint (`/saml/acs`) that accepts IdP POST responses, parses the XML, and displays the result visually. Includes support for `shared.js` layout/theme.
- **Metadata Generation**: Dynamic SP metadata available at `/saml/metadata`.

### User Sync (SCIM push + Graph pull)
- **SCIM 2.0 Server** (`scim-server.html`): the tool *is* the SCIM endpoint. Features an educational Step 0 lifecycle walkthrough (Discovery handshake, pre-flight existence check, user creation, delta PATCH sync, group sync, and deprovisioning). `/api/scim-admin` creates a private endpoint (`eid` = 16 hex chars + random bearer token). Entra ID provisioning pushes to `/scim/{eid}/v2` (`api/scim-server.js`): `Users`, `Groups`, `ServiceProviderConfig`, `ResourceTypes`, `Schemas`; GET/POST/PUT/PATCH/DELETE; filter (`attr op "value"`, `pr`), paging, `excludedAttributes`; PATCH handles Entra quirks (`Replace`/`Add` casing, `"True"/"False"` strings, path-less merges, `emails[type eq "work"].value`, `members` add/remove, enterprise extension URN paths). Every request (including 401/404) is logged with the bearer token and `password` values masked; the page shows log + provisioned state (auto-refresh 5s).
- **Graph API Pull** (`graph-pull.html`): **users only**. Features an educational Step 0 explaining M2M pull architecture vs SCIM push. Step 2 gets an app token (client credentials, scope `https://graph.microsoft.com/.default`) with client secret validation (detects secret ID GUID vs secret value, AADSTS7000215 handling). Step 3 is the **inclusion filter**: rows of Entra property + operator (`eq`, `ne`, `startsWith`, `endsWith`) + value, joined with `and`, built into an OData `$filter` (single quotes escaped; bool props unquoted; custom property names validated). Filters always add `ConsistencyLevel: eventual` + `$count=true` (advanced query). Also raw `$filter` override, `$select`, `$top`, paging (Next / Load all, max 50 pages). `api/graph-pull.js` is **not** an open proxy: only `https://graph.microsoft.com/{v1.0|beta}/users` is allowed.
- **Storage** (`api/_lib/store.js`): Upstash Redis over REST (global `fetch`, no dependency) when `KV_REST_API_URL`+`KV_REST_API_TOKEN` (or `UPSTASH_REDIS_REST_URL`+`UPSTASH_REDIS_REST_TOKEN`) are set; otherwise an in-memory fallback (local dev only — unreliable on Vercel). The Redis DB may be **shared with other projects**: every key is prefixed `agnft:scim:{eid}:{cfg|users|groups|log}`, all keys have a 7-day TTL (refreshed on write), only an allowlist of commands is sent (no KEYS/SCAN/FLUSH), and any key outside the prefix is rejected in code. Caps: 1000 users and 1000 groups per endpoint, 200 log entries.
- **Routing**: `vercel.json` maps `/scim/([^/]+)/v2/?(.*)` to `/api/scim-server?eid=$1&path=$2`; `dev-server.js` has the equivalent regex and refuses `/api/_lib/*`. `api/_lib/` starts with `_` so Vercel does not deploy it as a function.
- Design/plan: [docs/user-sync-plan.md](docs/user-sync-plan.md).

### UI/UX Standards
- **Centralized Layout**: Header and Footer are centrally managed via `shared.js` (`injectLayout()`) to ensure consistency across all pages (including backend-driven HTML responses).
- **Step-by-Step Flow**: Each flow is broken into "Step Cards" starting from **Step 0**.
- **Tile-based Flow Selection**: Homepage uses an high-visibility card layout with implementation badges (e.g., Browser-only vs Proxy).
- **Terminal View**: Requests are rendered in a terminal-style block showing Method, URL, and Body.
- **Auto-Save**: Form inputs are persisted in `sessionStorage` via `attachAutoSave` in `shared.js`.
- **Auto-Scroll**: The page automatically scrolls to new results (e.g., after receiving a code or token).

## 🖥️ Local Development

```bash
npm install
node dev-server.js
# Serves at http://localhost:3001
```

SCIM storage uses the in-memory fallback locally. To use Upstash Redis set `KV_REST_API_URL` + `KV_REST_API_TOKEN` (Vercel: connect the Upstash DB under Storage). Entra ID cannot reach localhost — use the deployed site or a tunnel (ngrok) for real provisioning.

For full Vercel environment simulation:
```bash
vercel dev
```
